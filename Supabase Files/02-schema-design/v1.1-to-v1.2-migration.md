# V1.1 → V1.2 Migration Guide

This document describes how to move a V1.1-conformant (or, for TU Delft, pre-V1.1) `records.json` to V1.2. It is the narrative companion to the per-institution `migration-report.md` files under `03-migrated-runs/*/`, which record what actually happened for each of the five datasets. Read this first for the general rules; read each institution's own report for its specific field-by-field trace.

## Zero data loss is the hard constraint

No source fact may disappear merely because V1.2 restructures where it lives. Every fact that existed in a V1.1 field must land in exactly one of these places in V1.2:

1. A renamed or relocated canonical V1.2 field (the common case — most V1.1 data migrates untouched).
2. A newly promoted canonical V1.2 field or entity (when the V1.1 shape was an `extension_metadata` workaround or a forced misrepresentation that V1.2 now resolves properly).
3. `extension_metadata`, unchanged, when the V1.2 gap-matrix disposition for that fact was C (keep as extension) or D (defer).
4. An explicit, logged entry in that institution's `migration-report.md` flagging the fact as **unmapped** — this is the only acceptable outcome for a fact that truly has no home in V1.2 yet, and it must never simply be dropped silently.

## ID stability

Canonical IDs (`nl-tu-delft`, `gb-university-of-oxford`, `ca-university-of-toronto`, `de-tu-munich`, `ae-nyu-abu-dhabi`, and every ID derived from them) do not change in V1.2. No ID was renamed for aesthetic reasons. New entities introduced in V1.2 (`College`, `ProgramPathway`, `AdmissionStage`, `DecisionPlan`, `FinancialRequirement`, `FinancialAidPolicy`) mint new IDs following the same country-prefixed, institution-inherited convention as all existing entities (e.g. `gb-university-of-oxford-college-<slug>`, `ae-nyu-abu-dhabi-admission-stage-<slug>`). Because no existing ID changes, **no `v1.1-to-v1.2-id-remap.json` file is produced** for any of the five institutions — each institution's `migration-report.md` states this explicitly rather than silently omitting the file.

## Structural changes every migration must apply

1. **`schema_version`** → set to `"1.2"` on the top-level object.
2. **Five new required top-level arrays** must be present on every migrated `records.json`, even when empty: `colleges`, `program_pathways`, `admission_stages`, `decision_plans`, `financial_requirements`, `financial_aid_policies`. An institution with no evidence for a given new entity type still includes the array as `[]` — never omits the key.
3. **`Program.campus_ref`**: if a V1.1 record held a synthetic/fabricated campus reference solely to satisfy V1.1's required-field constraint (Oxford's case), the migration replaces it with `null` and logs the removal of the fabricated value in the migration report. Institutions with a genuine single campus keep their real `campus_ref` unchanged.
4. **`CostProfile.living_cost_source_basis.kind`**: any V1.1 record using `visa_proof_of_funds_deposit` is migrated by (a) creating a new `FinancialRequirement` record carrying that same amount, currency, and source evidence, with `requirement_type` set from context (`visa_proof_of_funds` for TU Delft's IND deposit, `blocked_account` for TU Munich's Sperrkonto), and (b) either removing the now-invalid `kind` value from the `CostProfile` (if no genuine living-cost estimate exists separately) or correcting `kind` to whichever narrowed value actually applies if a genuine estimate coexists. The original V1.1 fact is never deleted — it is relocated to its structurally correct home and the relocation is logged.
5. **`VerificationRecord.material_extension_fact`**: any V1.1 record using the informal additive convention (TU Munich, NYU Abu Dhabi) is migrated by moving that same boolean into the now-formal schema field of the same name. No value changes, only its status from informal-convention to schema-defined.
6. **`verification_status` `VERIFIED_ABSENT`**: any V1.1 `VerificationRecord` using the informal `absence_claim: true` additive boolean is migrated by setting its formal `verification_status` to `VERIFIED_ABSENT` (replacing whatever status — typically `VERIFIED` — it held informally alongside the additive flag in V1.1). The underlying claim and its source_refs are unchanged.

## Per-institution migration notes (summary; full detail in each `migration-report.md`)

- **TU Delft** — migrates from a **pre-V1.1** ad hoc shape, not from a hardened V1.1 baseline like the other four. Its `records.json` predates the V1.1 hardening pass entirely: no `schema_version`, no `run_id`, no `derived_cost_estimates` array, non-canonical field names (`total_credits`, `language_notes` on `Program`; `standardized_tests[].required_or_recommended` instead of `.required`), and a **string-typed** `source_records` field (a path reference, "see runs/.../sources.json") rather than an array of `SourceRecord` objects. This migration is therefore a two-step move in one pass: pre-V1.1 → V1.1-canonical field names → V1.2 additions, all performed together and fully documented in TU Delft's `migration-report.md` since no intermediate V1.1-conformant artifact for TU Delft has ever existed. Its IND proof-of-funds deposit (`kind: visa_proof_of_funds_deposit`) becomes a `FinancialRequirement` record per rule 4 above. Its `source_records` string is resolved by loading the actual `sources.json` referenced and materializing it as a proper `SourceRecord` array.
- **Oxford** — its synthetic central-campus `Program.campus_ref` is nulled per rule 3. Its BA→MCompSci integrated continuation becomes a `ProgramPathway` (`pathway_type: integrated_continuation`). Its collegiate system becomes `College` records referenced from `Scholarship.college_ref` and `CostProfile.college_ref`. Its monthly living-cost range becomes `CostProfile.estimated_living_costs_monthly_range`. Its UCAS application code/deadline becomes a `DecisionPlan` (`plan_type: single_stage`, `application_platform: "UCAS"`).
- **Toronto** — its `AdmissionStage`/`ProgressionRequirement` concepts (Toronto's own V1.1-era naming, not yet schema-formalized) become canonical `AdmissionStage` records (`stage_type: faculty_entry` and `stage_type: progression` respectively) plus a `ProgramPathway` for the Specialist/Major/Minor structure. Its explicit contradiction of Oxford's College hypothesis is preserved by simply having zero `College` records — no forced college data is invented.
- **TU Munich** — its `ApplicationStage`/`SelectionProcedure`/`SelectionCriterion`/`SelectionStage` cluster (TUM's own V1.1-era naming) collapses into `AdmissionStage` records with embedded `criteria[]`, one record per selection stage, `sequence_order` preserving the original ordering. Its `QualificationRecognitionPathway` becomes an `AdmissionStage` with `stage_type: qualification_recognition`. Its Sperrkonto figure becomes a `FinancialRequirement` (`requirement_type: blocked_account`) per rule 4. Its semester-denominated duration now uses `duration_unit: semesters` directly instead of a lossy years conversion.
- **NYU Abu Dhabi** — its university-wide holistic admission step becomes an `AdmissionStage` (`stage_type: university_entry`, `program_ref: null`). Its disputed major-declaration deadline becomes an `AdmissionStage` (`stage_type: major_declaration`) — the HUMAN_REVIEW conflict between its two source deadlines is preserved unchanged, now attached to the stage record rather than to `Program`. Its ED I/ED II/RD structure becomes three `DecisionPlan` records. Its test-optional policy becomes `Program.testing_policy`. Its CSS-Profile-based individualized need-based aid becomes a `FinancialAidPolicy` record with no numeric award amount; its one genuinely fixed award (Sheikh Mohamed bin Zayed Scholarship) remains a `Scholarship` record, unchanged in kind.

## Validation gate

A migrated `records.json` is not considered complete until it passes all of: `validate_normalized_records_v1_2.py` (schema conformance), `check_fields_supported_v1_2.py` (every canonical field traces to a real source path), and `check_verification_coverage_v1_2.py` (field-level, meaningful-absence, and material-extension coverage) — see `04-pipeline/`. No migrated dataset is presented as complete without all three passing.
